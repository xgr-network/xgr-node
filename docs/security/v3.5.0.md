## Attack and admission boundary

Legacy staking accepted arbitrary BLS bytes without proving ownership. An
attacker can register `PK_X - PK_V`, so aggregation with victim `PK_V` yields
`PK_X`. One signature by `SK_X` then falsely counts both identities. Stake-based
quorum arithmetic cannot distinguish this false attribution.

The independent regression `TestRogueKeyForgeryAndPossessionAdmission` recreates
the cancellation using ephemeral local keys and calls the real legacy
`BLSKeyManager.VerifyCommittedSeals`. It confirms acceptance of two alleged
signers, rejection of the ordinary-key control and rejection of the rogue key's
possession proof. The legacy mathematical verifier remains available for
historical replay. Post-fork consensus supplies it only independently admitted
keys, including when the validator set came from a canonical cached snapshot.

The advisory body was read. Its original attached scripts could not be read:
the browser returned `ERR_BLOCKED_BY_CLIENT`. This release's tests are an
independent reproduction, not execution of those original scripts.

## Possession statement

The signed message is:

```
keccak256(abi.encode(
    keccak256("XGR_STAKING_BLS_POP_V1"),
    chainId, stakingContract, validatorAddress,
    keccak256(compressedPublicKey), nonce
))
```

The public key is part of the statement. Address, chain, contract and nonce
binding prevent proof transplantation and consumed-proof replay. Go validates
length, subgroup, identity and canonical key encoding. Solidity uses the native
`0x2040` verifier with a singleton key set. No consensus signature format or
XITA admission domain is changed. The legacy proofless selector always reverts
in the candidate runtime. Every subsequent registration, including returning to
a previously proved key, requires a fresh nonce-bound signature.

## One activation height

`stakingBlsPoP` is the sole new consensus gate. Its optional configuration has no
implicit activation. The manifest commits to the same H and chain ID; its
digest and public proofs are configuration evidence, not additional gates.

At H, `Executor.BeginTxn` invokes the IBFT upgrade hook before user transactions.
This shared path serves proposal building and finalized-block execution. If the
fork is active without the required hook, execution fails closed.

Before any write, the hook checks the frozen legacy runtime and proves exact
coverage of the union of all registered nonempty BLS keys, including inactive
validators, and the canonical macro snapshot signing H. Missing evidence does
not reduce quorum or grandfather a key: migration fails. Only after all checks
does it replace code and write the independently proved history entries,
consume nonce-zero migration proofs and store the manifest digest.

The set signing H is still selected from H-1. ForkManager validates that set
against a temporary parent-state transition with the same deterministic upgrade;
it does not trust H's proposed post-state. Normal, active-emergency and
stake-emergency selection all exclude unproved keys thereafter. Historical
verified keys are retained because a macro snapshot may outlive key rotation.
ParentCommittedSeals select modules and PoP requirements at the parent's height.

The persisted marker makes post-state queries at H idempotent and supports
restart/fresh sync. A missing marker after H or mismatched marker/runtime stops
execution. Legacy staking redeployments or a non-BLS/PoS schedule overlapping H
are rejected during configuration validation.

## Storage and balances

The system address and slots 0 through 10, including nested struct member
layouts, are unchanged. New storage is:

| Slot | Data |
| --- | --- |
| 11 | address → public-key hash → verified possession |
| 12 | address → next registration nonce |
| 13 | migration manifest digest |

The compiler build compares every old field's slot, offset and recursively
resolved type with the candidate prefix. Tests also check all existing fixture
words, account balance, a retained history sentinel, the complete migration
write footprint and cross-check Go/Solidity mapping readers. No balance transfer,
stake reset, delegation rewrite or weight reset is performed by migration.
The historical bootstrap bytecode remains frozen in the existing helper.

## Determinism and evidence

Manifest entries are strictly ordered by address and compressed key. Multiple
different keys for an address are permitted only when required by registered
state/snapshot coverage. Duplicate pairs, malformed/noncanonical encodings,
unknown/duplicate JSON fields, wrong contexts and invalid signatures are
rejected. The digest uses domain-separated fixed-width binary encoding, not
map-dependent JSON serialization. No `verified` boolean from a manifest is
trusted. Every node independently verifies the signatures at initialization.

`scripts/build-staking-pop.mjs --check` recompiles with locked solc 0.8.30,
optimizer runs 200, Shanghai EVM target and no metadata trailer. The checked-in
ABI/runtime/layout artifact is independently comparable. Go validation uses the
repository's declared 1.23.11 toolchain.

## Limits and remaining deployment risks

- Actual production proofs require each operator's existing local BLS key.
  Test proofs must never be used for production.
- The chosen manifest must cover H's actual parent state and canonical snapshot.
  A pre-H registration/rotation or lost historical key can make a prepared
  manifest incomplete and cause an intentional halt at H.
- Nodes must agree on code, height, manifest and digest before activation.
  Configuration disagreement is a consensus risk.
- Historical blocks before H retain historical verification rules. This change
  does not retrospectively establish possession for historical keys.
- A proof establishes key possession; it does not establish operator independence
  or decentralization, and it does not replace XITA's separate membership proofs.

An initial devnet attempt was automatically stopped when the optional Interchain
worker attempted a production Base RPC. The test was changed to explicitly
disable worker construction before any external-chain operation. The successful
isolated test uses loopback peers and that tested disable path. No exploit test
or transaction was directed at a public chain.
