## Conclusion and limits

The internal source review found no additional Critical or High issue in the
candidate possession admission and migration paths examined. The candidate is
ready for the reporter's private code review. This is not a Mainnet activation
approval, an external audit, or a guarantee that no vulnerability remains.

Mainnet release prerequisites remain: independently obtained genuine proofs for
all required keys, matching configuration/manifest digests across every node,
parent-state and macro-snapshot inventory, an explicitly approved activation
height, a production-configuration rehearsal and a quorum-preserving binary
rollout. No production keys or public RPC attack tests were used in this review.

## Explicit operational risks and reporter suggestions

1. Legacy registration remains exposed until H. A malicious or merely changed
   pre-H key can invalidate the frozen manifest and halt activation. Monitor the
   roster, avoid planned key churn, inventory inactive registered keys too, and
   revalidate just before scheduling. If coverage changes, regenerate the agreed
   manifest/configuration before H; do not grandfather keys or reduce quorum.
2. Complete coverage is required, not just quorum with a margin. The hook rejects
   missing, extra, malformed and unproved entries. This prioritizes deterministic
   safety over availability if the rollout is misconfigured. A chain halt on bad
   preparation is a known consequence, not a claim of automatic recovery.
3. Startup rejects missing evidence, invalid proofs, wrong chain/height and a
   manifest/digest mismatch when the gate is configured. Two independently valid
   but different configurations cannot be detected from a node's own config
   alone. An omitted gate remains intentionally inactive. Deployment must compare
   the exact approved configuration and manifest digests out of band.
4. Prefer an agreed macro boundary for production operations; the implementation
   must still protect retained snapshots and is tested at other boundaries too.
5. Duplicate BLS public keys across distinct addresses are not newly forbidden.
   Each address needs its own bound proof and stake-based voting identity. A
   shared private key does not forge an honest independent key, but concentrates
   operator/key risk. Check production keys are distinct. Global duplicate-key
   rejection is deferred rather than silently changing historical consensus or
   introducing a later set-selection halt on a valid registration.
6. A second runtime/enforcement fork was not introduced. Public proofs are
   collected before H using the existing CLI; code replacement, verified state,
   registration interface and consensus admission activate together at H.
7. Original advisory attachment downloads were blocked by the browser. The
   independent local cancellation test reproduces the actual legacy verifier's
   acceptance and ordinary-key negative control; it does not claim execution of
   the original scripts. The reporter should compare their original reproducer.

## Reproduce the candidate locally

Use a private checkout with the baseline Git history available. Check out the
exact candidate hash from the handoff. Do not merge or publish the branch.

```sh
git rev-parse HEAD
git merge-base --is-ancestor 0d9aca695c49784da64736d78620cc1bba4f7daa HEAD
bash scripts/validate-v3.5.0.sh
```

Requirements: Git, Node/npm, a Go launcher able to run Go 1.23.11, and a normal
local Linux build environment. The script pins the compiler through npm's lock
file, verifies the artifact and recursive storage prefix, runs the selected
regression suites, compiles all Go packages, builds a local node binary and runs
only the isolated fork devnet. Optional `GO_BINARY` selects the Go launcher;
`XGR_V350_BUILD_DIR` selects its binary output directory.

For focused checks:

```sh
GOTOOLCHAIN=go1.23.11 go test ./crypto ./consensus/ibft/blspop ./consensus/ibft/fork ./state ./command/ibft/blspop ./command/ibft/join ./validators/store/contract
GOTOOLCHAIN=go1.23.11 go test ./consensus/ibft/blspop -run 'TestRogueKeyForgeryAndPossessionAdmission|TestConsensusVerifierRejectsInfinitySignatureAndAggregateKey' -count=1 -v
GOTOOLCHAIN=go1.23.11 go test ./state -run '^TestStakingPoP' -count=1 -v
```

The legacy forgery regression intentionally observes acceptance with rogue keys
and rejection of the ordinary-key control; the candidate blocks admission of the
rogue key. A passing test does not mean the legacy mathematical verifier itself
was globally changed.

For manual migration preparation use `docs/security/v3.5.0-rollout.md`: run
`ibft bls-pop proof` with each validator's existing local secrets, collect only
public JSON, run `assemble`, `verify` and `configure`. No rollout automation script
was added. Never collect private keys on a manifest assembly host.
