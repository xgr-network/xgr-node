# v3.5.0 private Mainnet rollout and recovery procedure

> **Rollout update (2026-11-05):** v3.5.0 is published and Mainnet activated at **12,586,649**; Testnet at **6,613,834**. See the [current release, canonical genesis and verification record](https://github.com/xgr-network/XGR/blob/main/docs/chain/XGRCHAIN_v3.5.0_Release_and_Activation.md). The dated private-review/pre-activation procedure below is retained as historical review evidence; it is not an instruction to choose a new height or repeat migration. Advisory publication remains a separate action.

This document prepares a rollout; it authorizes no deployment, activation,
public merge, release publication or advisory publication. No production height
has been selected in this branch. Test activation heights are isolated fixtures.

## 1. Review and build

1. Review the final private commit, the advisory and
   `docs/security/v3.5.0.md`. Obtain the original researcher scripts for comparison
   if available; the automated browser could not read those attachments.
2. Clone the temporary private fork in a trusted build environment. Use the
   exact reviewed commit. Keep review branches and outputs private.
3. Run `bash scripts/validate-v3.5.0.sh` with Go 1.23.11, Node and npm available.
   It verifies locked compiler output, storage layout, the relevant Go tests,
   full compilation and the isolated fork/restart/fresh-sync test.
4. Prepare the versioned binary from that clean reviewed checkout using:

   ```sh
   make -f scripts/Makefile build VERSION=v3.5.0
   ./xgrchain version
   sha256sum ./xgrchain
   ```

5. Record the actual commit, binary checksum, embedded version and candidate
   contract artifact checksum. Do not publish a tag or release yet.

## 2. Collect public proofs without moving funds

Select H only with explicit Mainnet approval. Inventory **all** registered
nonempty keys, including inactive candidates, and the canonical macro snapshot
that will sign H. If a snapshot retains an older key, prove that key too or
select a later safe boundary before activation with coordinated approval.
Keep key registration/rotation and validator exit plans stable during this
preparation window. Delegated balances are not part of a possession proof.

On each validator, run the candidate binary against its existing local secrets:

```sh
./xgrchain ibft bls-pop proof \
  --data-dir /existing/validator/data \
  --chain-id 1643 --out validator-public-proof.json
```

The command reads the existing ECDSA/BLS keys locally, signs automatically and
writes only public evidence. It creates no replacement keys, submits no
transaction and requires no wallet confirmation. The cloud secrets-manager
configuration remains available through `--config` instead of `--data-dir`.
Never copy or export private keys to an assembly host.

Collect the public files and assemble them in any input order:

```sh
./xgrchain ibft bls-pop assemble --chain-id 1643 \
  --activation-height "$H" \
  --proof validator-1-public-proof.json \
  --proof validator-2-public-proof.json \
  --proof validator-3-public-proof.json \
  --proof validator-4-public-proof.json \
  --out staking-pop-manifest.json

./xgrchain ibft bls-pop verify --chain-id 1643 \
  --activation-height "$H" --manifest staking-pop-manifest.json
```

Add a proof argument for every required address/key pair, including additional
validators and retained historical snapshot keys. The four-file example is not
a hardcoded Mainnet validator count. Every operator independently verifies the
same canonical manifest and compares its full digest. Offline verification
proves the signatures; exact parent-state/snapshot coverage is also enforced by
each node at H.

## 3. Prepare a separate configuration

```sh
./xgrchain ibft bls-pop configure \
  --chain existing-genesis.json --manifest staking-pop-manifest.json \
  --activation-height "$H" --out genesis-v3.5.0-candidate.json
```

This writes a separate file and preserves the input. It adds only:

- `params.forks.stakingBlsPoP.block = H`;
- `params.stakingBlsPoPMigration.manifest`, containing the canonical public JSON
  as an escaped string;
- `params.stakingBlsPoPMigration.digest`, computed from verified evidence.

An existing conflicting PoP height or manifest is rejected. Other forks,
allocations and engine fields are preserved. The command does not deploy or
activate anything. Review the diff and independently compare the full new
configuration and manifest digests across validators, RPC nodes and observers.

Do not enable `interchainRuntimeDisabled` on production nodes as part of this
rollout unless separately intended. That local option exists for isolated tests;
it is neither a PoP gate nor an alternative migration path.

## 4. Approved binary rollout and activation

Only after explicit authorization:

1. Back up each node's configuration, version/checksum inventory and recoverable
   database state. Keep validator secrets protected on their original nodes.
2. Install the reviewed binary and approved candidate configuration on all
   validators and supporting nodes sufficiently before H. Restart in a sequence
   that preserves quorum. Check startup validation and continued pre-H sealing.
3. Confirm that no legacy staking redeployment or non-BLS/PoS transition overlaps
   H. Startup configuration validation rejects those conflicts.
4. Immediately before H, recheck the required registered and snapshot keys
   against the agreed manifest. Resolve any new key before activation; do not
   plan to mark a key verified manually.
5. At H, observe automatic migration. Nodes replace runtime code and write only
   independently proved status/history, consumed migration nonces and the
   manifest marker. No stake/delegation transaction or balance transfer occurs.
6. Compare block hash and State Root at H and H+1 across independent nodes.
   Verify the staking runtime, `blsPoPMigrationHash()`, preserved stake/delegation
   state and a normal epoch transition. Check all validators remain represented
   as intended by the canonical snapshot and weights.
7. Verify a restarted node and a fresh syncing observer. Confirm normal XITA
   service health separately using ordinary monitoring, without attack tests.

New registrations/rotations use `registerBLSPublicKey(bytes,bytes)` and the
current `blsPoPNonce(address)`. `ibft join` does this automatically. Do not send
the legacy proofless call at or after H. A transaction prepared immediately
before H with the legacy selector can revert after activation; prepare it again
with the upgraded runtime visible.

## Recovery before H

If evidence, compatibility or operator readiness is incomplete, stop the rollout
before activation. Coordinate any cancellation or approved replacement H across
**all** nodes. Restore the previous configuration consistently while the fork
is still in the future. Do not let nodes use divergent heights or manifests.
There is no need to unstake or transfer funds to cancel an unactivated plan.

## Recovery at or after H

- Missing/invalid proofs, unexpected legacy code or coverage mismatch fail
  closed. Do not bypass the check, fabricate proof status or remove an offending
  validator merely to get a smaller quorum.
- Preserve logs, the agreed configuration, manifest, binary checksum and the
  last agreed block/root. Determine whether any H block was actually finalized.
- If H was finalized, do not downgrade to v3.4.3, remove the gate or run mixed
  configurations. A post-H marker/runtime mismatch requires coordinated repair
  using the agreed history and reviewed code.
- Restore an affected node from a consistent backup or fresh-sync it using the
  same reviewed post-fork binary/configuration. Migration is idempotent for
  already migrated state; it must not consume migration nonces a second time.
- A network-wide change to an already finalized activation requires a separate
  reviewed recovery decision. This candidate supplies no emergency admin
  bypass, automatic rollback or stake-reset mechanism.

Publish the release/advisory only under separate explicit approval after the
coordinated deployment and disclosure decision.
